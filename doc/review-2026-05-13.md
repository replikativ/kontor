### P0 — ship-blockers / correctness

#### P0-1. `ADR-044` is cited from kernel schema but does not exist in `doc/decisions.md`

`src/kontor/schema.clj:3231`:

```
bitemporal-tx-attrs)))                ; ADR-044 (experimental)

But `doc/decisions.md` jumps `ADR-043` → `ADR-048`. There is no `ADR-044`, `ADR-045`, `ADR-046`, or `ADR-047`. The actual ADR for `:tx/valid-from` / `:tx/valid-to` and the per-posting drop is **ADR-048** at `doc/decisions.md:4687`. #### P0-2. Kernel schema docstring still advertises `:posting/temporal-key` and per-posting `:*/valid-from`/`valid-to`

`src/kontor/schema.clj:11-16`:

```
   Bitemporal modeling per ADR-008:
     - transaction time = :db/txInstant (datahike-supplied, free)
     - valid time       = explicit :*/valid-from and (where applicable)
                          :*/valid-to attributes on transactions and
                          postings.
     - the :posting/temporal-key tuple indexes the bitemporal axis.
```

All three of those statements are now false after ADR-048 (`doc/decisions.md:4687`). Valid time lives on the tx via `:tx/valid-from`. There is no per-posting `valid-from`, no `valid-to`, no `temporal-key`. A new reader landing on `schema.clj` will form a wrong mental model that contradicts the implementation in `src/kontor/posting.clj:351-353` (`kbt/with-vt`) and the resolver in `src/kontor/bitemporal.clj:212-225`.

#### P0-3. `doc/architecture.md` is wholesale stale relative to ADR-048 (and ADR-031, 034, 037, 042, 043)

`doc/architecture.md:139` still lists `:posting/valid-from` as a posting attribute. `doc/architecture.md:153` says "Filters `(<= :posting/valid-from valid-time)` …" — that attribute no longer exists. The kernel-namespaces list at `doc/architecture.md:103-118` does not mention `:status-transition/*`, `:status-history/*`, `:audit-doc/*`, `:approval-policy/*`, `:partner-merge/*`, `:bank-account/*`, `:partner-tax-id/*`, `:side-effect-intent/*`, `:account-type-direction/*`, `:payment-application/*`, `:entity/*`, `:schedule/*`, `:valuation-book/*`, `:valuation-layer/*`, `:attestation/*`, `:complemento/*`, `:country/*`, `:state/*`, `:ledger/*`, `:analytic-plan/*`. None of those exist in the document despite being central to Stages H-L. Treated separately in section 3.

#### P0-4. Two parallel invoice implementations with divergent semantics

There are now two invoice surfaces:

- `src/kontor/invoice.clj` (`kontor.invoice/{create!, send!, mark-paid!, cancel!}`) — predates the status machine (ADR-034). Lines 200-227 + 224-228 + 254-256 flip `:invoice/status` directly with `d/transact`. **No `:status-history` row is written.** Sealing comment at `src/kontor/invoice.clj:281-282` writes `:transaction/state :posted` + `:transaction/posted-at` together but never opens the audit trail required by ADR-038 (`reason`, `changed-by-uid`, `reason-note`, `supporting-doc`).
- `modules/invoice/src/kontor/invoice/{posting.clj,bridge.clj}` (`kontor.invoice.posting/post-to-ledger!`, `kontor.invoice.bridge/*`) — uses `sm/record-status-change-tx-data` (`modules/invoice/src/kontor/invoice/posting.clj:303`, `bridge.clj:114, 134, 148`) — the correct, ADR-034+038 compliant path.

Either delete `src/kontor/invoice.clj` or port it to the status machine. Today, depending on which fn a consumer reaches for, they get audit history or they don't. That is unsafe for an "audit-by-default" kernel. The cleanest path is to delete `src/kontor/invoice.clj` and migrate its callers (showcase 1 calls `(d/transact ...)` directly, so likely zero callers depend on the old API outside its own tests).

#### P0-5. `kontor.collections/credit-hold` writes raw rows, bypassing the status machine

`modules/collections/src/kontor/collections/credit_hold.clj:201-256`. `place-hold!` and `release-hold!` write `:credit-hold/placed-at`, `:credit-hold/released-at` directly. They accept neither `:vt-from`/`:vt-to` (cf. `case.clj:107-149`, `dispute.clj:90-200`, `promise.clj:88-181`) nor write a `:status-history` row to anchor the "active" predicate. The schema's `:credit-hold/state` attribute does not exist; the active-vs-released decision is keyed off whether `:released-at` is non-nil (`modules/collections/src/kontor/collections/schema.clj:273-279` doc), and the schema even comments that it lives on the row "for audit" — but the row is the only record. By contrast, `dispute`, `case`, `promise` write a row plus a `:status-history` row plus stamp `:tx/valid-from`. Credit-hold is the outlier.

Decide one of:
- (a) Treat `credit-hold` as a row-presence entity (no state machine, no valid-time). Then the schema doc and ADR-038 SoD enforcement must be tightened to explain that approvals on these rows are tx-time only.
- (b) Bring `credit-hold` in line with `dispute`/`promise`/`case`: introduce `:credit-hold/state` (`{:placed :released :expired}`), wire status transitions, accept `:vt-from`/`:vt-to`, write `:status-history`.

ADR-048 implicitly assumes (b); the schema today is (a). This is the most visible piece of leftover work from `e25e8f8 Remove status-transition denorms; port transactors to tx-meta valid-time`.

#### P0-6. The kernel does *not* close over the status-transition denorm purge — collections still carries seven of them

`e25e8f8` (commit message: "Remove status-transition denorms") removed them on `:invoice/*` and `:dispute/*`. But the same pattern remains on:

- `modules/collections/src/kontor/collections/schema.clj:52` `:collection-case/opened-at`
- `modules/collections/src/kontor/collections/schema.clj:56` `:collection-case/closed-at`
- `modules/collections/src/kontor/collections/schema.clj:159` `:payment-promise/recorded-at`
- `modules/collections/src/kontor/collections/schema.clj:265` `:credit-hold/placed-at`
- `modules/collections/src/kontor/collections/schema.clj:273` `:credit-hold/released-at`
- `modules/collections/src/kontor/collections/schema.clj:481` `:dunning-pause/placed-at`
- `modules/collections/src/kontor/collections/schema.clj:494` `:dunning-pause/released-at`

`:collection-case/opened-at` is used inside a *tuple identity* (`schema.clj:104-110`), so it cannot simply be dropped without rethinking how "one open case per (partner, entity)" is enforced — possible alternatives: a partial unique index over `[:partner :entity]` filtered to non-closed; or a separate `:collection-case/sequence-no` per (partner, entity). The point is that what was sold in ADR-048 as a clean "drop the denorms; resolve via `kbt/timeline`" did not land for the collections module. Either ship the rest of the cutover or document explicitly in ADR-048 (or a follow-up ADR-049) why these survive.

### P1 — drift, stale docstrings, half-finished migrations

#### P1-1. Transactor opts shape is *almost* uniform but not quite

The healthy pattern across the codebase is:

```clojure
;; opts shape (de-facto kernel convention)
{:vt-from         #inst "..."   ; default: now (or :transaction/effective-date)
 :vt-to           #inst "..."   ; default: kbt/forever
 :changed-by-uid  <ref>          ; required for status-bearing entities
 :reason          :keyword       ; codified vocabulary (ADR-038)
 :reason-note     "free-text"
 :supporting-doc  <ref>}         ; ADR-038
```

This is uniform in:

- `src/kontor/payment_application.clj:200-280` and `300-401`
- `src/kontor/status_machine.clj:230-330`
- `modules/procurement/src/kontor/procurement/receipt.clj:218-310`
- `modules/collections/src/kontor/collections/{case,dispute,promise}.clj`
- `modules/collections/src/kontor/collections/writeoff.clj:116-219`

It is broken or partial in:

- `src/kontor/invoice.clj:155, 222, 241` — accepts `:vt-from`/`:vt-to` but ignores `:changed-by-uid` and `:reason`. See P0-4.
- `modules/collections/src/kontor/collections/credit_hold.clj:217, 247, 260` — accepts neither vt nor reason. See P0-5.
- `modules/collections/src/kontor/collections/pause.clj:58, 84` — same gap (worth a spot-check).
- `kontor.posting/build-transaction` (`src/kontor/posting.clj:290-353`) — accepts neither vt nor reason directly; it derives vf from `:transaction/effective-date`. That's fine for normal flow but means callers who want backdated corrections must wrap the return in `kbt/with-vt` themselves. Document this explicitly on the docstring (currently silent at lines 290-327).

Recommend: write down the canonical opts shape as a doc-only entity in `doc/architecture.md` or a brief `doc/conventions.md`, then audit each public transactor against it. A linter-grade rule: if a fn writes a `:db.type/instant` attribute named `*-at`, it must accept `:vt-from`/`:vt-to`.

#### P1-5. `posting/build-transaction` accepts `:transaction/posted-at` only by accident

`src/kontor/posting.clj:290-353` does not bake in sealing. Showcase 1 (`doc/showcases/01_de_b2b_factur_x.clj:210-214`) writes:

```

…directly via `d/transact`, completely bypassing `build-transaction`. There is no kernel-level helper for "build a balanced transaction and seal it in one move" or "transition from draft to posted (writes `:transaction/posted-at`, sets `:posting/posted-at` on every child posting, writes `:status-history`)." That last bit — *propagating `:posted-at` from the parent transaction to every child posting* — is mentioned in `src/kontor/schema.clj:1482-1488` as a hard invariant ("Set together with parent transaction's `:transaction/posted-at`") but only enforced by the sealing middleware, not by a builder. #### P1-6. ADR-008 wording in `decisions.md` is now incompatible with ADR-048 — both are "current"

`doc/decisions.md:125-152` (ADR-008) says: "Valid time = `:posting/valid-from` on every posting; `:transaction/effective-date` on every header." ADR-048 (`decisions.md:4687-4753`) overrides that. #### P1-9. `kontor.core/schema-summary` namespace allow-list will silently miss new namespaces

`src/kontor/core.clj:107-141` hard-codes the set of namespace strings to include in the schema dump. This set has not been updated since (visible) Stage I; it includes `partner-merge` etc. but is missing newer namespaces like `collection-case`, `payment-promise`, `dispute`, `dunning-policy`, etc. once those companion schemas are installed. #### P1-10. The `import_` directory hyphen-vs-underscore mismatch is jarring

Worth a short comment in `src/kontor/import_/.clj-package-info` (or just at the top of beancount.clj) explaining "this is `import_` because `import` is reserved at the JVM level."

```markdown
# kontor

A **double-entry accounting kernel** for Clojure. One dependency
([datahike](https://github.com/replikativ/datahike)). Bitemporal,
EPL-1.0, no UI, no ERP, no country-specific data bundled.

`kontor` ships the ledger semantics — accounts, journals, balanced
postings, periods, sealing, tax-engine protocol, parallel ledgers,
analytic dimensions, multi-attestation clearance — and stops there.
Per-country charts, tax rates, and e-invoice schemas live in separate
companion modules. Network adapters (PAC, IRP, SEFAZ, Peppol AP,
Avalara) live in partner adapters that never bundle credentials.

If you've used Datomic or XTDB, this will feel like home: the
accounting state *is* the datalog query target. If you've shipped
on Odoo / NetSuite / Xero, this is the substrate you would have
built underneath them.

## Why kontor

Three load-bearing differentiators:

1. **Bitemporal by default.** Every query takes `:as-of-tx` (what the
   books knew when) and `:as-of-valid` (when the fact was true). A
   2026 restatement of a 2024 invoice picks up the tax rate legally
   in force on the original date, not today's rate. Auditors can
   ask "what did the books look like as filed on 2025-04-15"
   from the same data. No bolt-on temporal tables.
2. **One database, two schema namespaces.** kontor's attributes are
   namespaced so that consumers (`beleg`, `simmis`, your app) can
   write their own `:invoice/*`, `:customer/*`, `:lead/*` etc. into
   the same datahike connection without collision. Posting a sales
   invoice writes `:invoice/status` and the matching `:transaction`
   + `:posting`s atomically in one tx. ADR-002.
3. **Datalog audit trail.** State transitions are
   `:status-history` rows with `:reason`, `:reason-note`,
   `:supporting-doc`, and `:changed-by-uid`. ADR-038 codifies the
   vocabulary and SoD enforcement (`:no-self-approval`,
   `:requires-supporting-doc`). The audit story is a query, not an
   ETL pipeline.

## What's *not* in kontor

- No UI. Build it in beleg / simmis / your stack.
- No ERP. (We have a sales/invoice/procurement/collections companion
  set under `modules/`, but the kernel itself stays small.)
- No US sales-tax engine. We provide the `TaxProvider` protocol;
  customers integrate Avalara, TaxJar, or TaxCloud.
- No Peppol Access Point. The UBL is emitted; AP delivery is a
  partner adapter.
- No bundled API credentials, ever.
- No Odoo translation. Reference design only (FSF treats translation
  as derivative work; the licenses would propagate). ADR-001.

ADR-010 + ADR-037 explain the boundary in detail.

## Try it in five minutes

;; Ephemeral in-memory DB with the schema + primary ledger.

                 :transaction/narration     "INV-2026-0001"

                  :posting/amount     1000.00M

                  :posting/amount   -1000.00M

### The bitemporal pitch in one minute

A correction of an old fact is a *new write at a past valid-time*,
not an in-place edit. `kontor.bitemporal` exposes this directly:

```clojure
;; Correction: at 2026-06-20 we discover the May invoice's amount
;; was wrong. Write the fix with :vt-from = 2026-05-11 (the date
;; the corrected fact applies), and the tx-time is "today".
(d/transact
 conn
 (kbt/with-vt
   [{:db/id <invoice-eid>
     :invoice/total-net 950.00M}]
   #inst "2026-05-11"))

;; What did the books say on 2026-05-31, as known on 2026-05-31?
(kbt/value-at (kbt/as-of-bitemporal (d/db conn)
                                    {:tx #inst "2026-05-31"})
              <invoice-eid> :invoice/total-net
              #inst "2026-05-31")
;; => 1000.00M

;; What do we know NOW about the books on 2026-05-31?
(kbt/value-at (d/db conn) <invoice-eid> :invoice/total-net
              #inst "2026-05-31")
;; => 950.00M (the correction is visible)
```

Two axes, freely composable: tx-time (`d/as-of`) × valid-time
(`kbt/value-at`). XTDB calls this "polygon resolution"; we get the
same shape from a tx-meta attribute plus a small resolver.

### Section: "Bitemporal queries" (architecture.md:148-162)

**Status:** rewrite. This is the section most aggressively broken by ADR-048.

**Before:**

> as-of-valid — what was true in the world as of this valid date. Filters `(<= :posting/valid-from valid-time)` and `(or (nil? :posting/valid-to) (> :posting/valid-to valid-time))`.

That filter is incorrect against the post-ADR-048 schema (there is no `:posting/valid-from`).

**After:**

> ## Bitemporal queries (ADR-008, ADR-048)
>
> Every accounting query takes two implicit dimensions:
>
> - **tx-time** — what the database knew at this transaction time. Datahike supplies this for free via `(d/as-of db tx-or-instant)`.
> - **valid-time** — when the recorded fact was true in the world. kontor models this with one tx-meta attribute, `:tx/valid-from`, on the writing tx. Every datom in that tx inherits the valid-time. Readers resolve via `kontor.bitemporal/value-at` (single fact at a cutoff), `values-between` (a window), or `timeline` (full history of one (entity, attribute)).
>
> The two axes compose. `(kbt/as-of-bitemporal db {:tx t :vt v})` returns a HistoricalDB pinned at tx-time `t`; the resolver applied on top of it answers "what did we think the fact was at valid-time `v`, as known by tx-time `t`."
>
> Backdated corrections: wrap your tx-data with `(kbt/with-vt tx-data effective-date)`. The default `:vt-from` for postings is `:transaction/effective-date`; the default `:vt-to` is `forever`. Mid-flight corrections of a previous fact are *new writes at a past valid-time*, not in-place edits — append-only, audit-clean, ADR-007-compatible.
>
> ```clojure
> ;; Trial balance as of Dec 31 2024 as known on Mar 31 2025
> (trial-balance conn
>                {:as-of-valid #inst "2024-12-31"
>                 :as-of-tx    #inst "2025-03-31"})
> ;; Historical fact for one entity:
> (kbt/value-at db invoice-eid :invoice/total-net #inst "2024-12-31")
> ```
>
> Helpers in `kontor.query` make this ergonomic. The default — when neither parameter is passed — is now/now.

**Rationale:** this is *the* differentiated capability vs. every other open-source ledger (Beancount, GnuCash, hledger, ledger-cli, even open-source ERPs). The bitemporal pitch should be precise, current, and runnable.

### New section to add: "Status machine and the audit story" (between sections 7 and 8)

`status_machine.clj` + `:status-transition` + `:status-history` + ADR-038 audit governance is now central to the kernel and is invisible in the architecture doc.

Proposed section (~30 lines):

> ## Status machine and the audit story
>
> Every state-bearing entity (invoice, transaction, dispute, case, promise, receipt, requisition, payment-promise, …) carries a *facet* — a `:db.type/keyword` attribute like `:invoice/status` or `:dispute/state`. State changes go through `kontor.status-machine/record-status-change!` (or its `…-tx-data` sibling for atomic composition), which:
>
> 1. Validates against `:status-transition` rows (per (entity-type, facet, from, to)).
> 2. Writes a `:status-history` row with `:reason`, `:reason-note`, `:supporting-doc`, `:changed-by-uid`, `:changed-at`, `:origin-transaction`.
> 3. Stamps the writing tx with `:tx/valid-from` (default: now; explicit `:vt-from` opt for backdated transitions, e.g. migration).
> 4. Enforces governance — ADR-038's `:no-self-approval`, `:requires-supporting-doc`, `:requires-non-empty-reason-note` — per a per-facet `:approval-policy` row.
>
> "When did invoice X transition to `:paid`?" is a query over its `:status-history`, not a separate audit log. Restating the invoice's status at any past valid-time uses `(kbt/value-at db invoice :invoice/status cutoff)`. The audit story is *the same data* as the operational data.
>
> Per ADR-048, the timestamp denorms (`:invoice/sent-at`, `:dispute/opened-at`, …) have been removed in favour of the `:status-history` + `:tx/valid-from` resolution. A few legacy denorms remain on `collection-case`, `credit-hold`, `dunning-pause` and `payment-promise`; these are tracked as follow-ups.
