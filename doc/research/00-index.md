## What each report answers

**01 — Reuse and landscape.** What can we lift from Odoo (LGPLv3) without translating Python? Where does Tryton (GPLv3) fit? What chart-of-accounts data is publicly usable (DATEV SKR03/SKR04 sourcing options)? What's the plain-text-accounting kernel pattern (Beancount/ledger/hledger)? What JVM e-invoicing libraries solve the Factur-X/XRechnung/Peppol problem (Mustang APL2, phax/ph-ubl APL2)? Concludes: *write a small PTA-style kernel ourselves; lift CoA facts from Tryton/GnuCash/Odoo into per-country license-tagged data modules; wrap Mustang for German e-invoicing; defer UI and Peppol AP*.

**02 — Datahike versioning and hashing.** What does `datahike` actually expose for branching, commits, content addressing, history? Concrete API: `datahike.versioning` namespace, `branch!`/`branch-as-db`/`commit-as-db`/`branch-history`/`merge-db`, all stable. Two hashes: weak per-tx `:hash` (`clojure.core/hash` summed → 32-bit, must be replaced) and strong commit-id (SHA-512-derived UUID-5 over commit metadata). With `:crypto-hash? true` the EAVT/AEVT/AVET index nodes become a real Merkle tree. Gaps for accounting: cryptographic per-commit content hash, commit signatures, sealed/append-only branches. ~1-2 weeks of upstream work to close. Concludes: *audit story is potentially better than Odoo's per-row hash chain (Merkle DAG vs linear chain), but the leaf hash gap MUST be closed first*.

**03 — US and Canada coverage.** Canada is "Germany-hard" with a different shape (federal GST + 4 HST provinces + 3 PST/RST + Quebec QST). The US is the cliff — not the kernel itself but sales tax (~11,000 jurisdictions, no federal authority, ~24 SST states with free CSV data + 22 non-SST including all the big revenue states). Concludes: *recommended sequence DE → CA → US; design a `tax-provider` protocol from day 1 so SST CSV / static / Avalara-API impls all plug in; wrap don't compete on US sales tax*.

**04 — `datopia/invariant` fit.** What the lib does (declarative datalog invariants per attribute, throw-on-failure). Cost model (per-affected-attr query × four DB snapshots; sub-millisecond for typical postings). What it expresses well (sum-to-zero, account-active, commodity-match) vs not well (sealing, state machines, behavior constraints). Library is pinned to datahike 0.6.x and at risk of bitrot — we maintain it. Concludes: *hybrid — adopt invariant for state predicates, hand-roll behavior in middleware; bump to 0.8.x as a Phase-1 prerequisite*.

**05 — XTDB monetary + bitemporal patterns.** XTDB treats `BigDecimal` as a first-class type (no separate Currency type — model as parallel column). Bitemporal SQL ergonomics gain ~70% query boilerplate but cost ecosystem alignment. **XTDB's audit story is weaker than datahike's** (with our planned Track-B hardening) — no commit DAG introspection, no signature hook. Concludes: *stay datahike for Phase 1 (ADR-008 confirmed); consider a read-only SQL bitemporal-shim as a future ergonomic improvement*.

**06 — openclaw extraction inventory.** The user's prior exploratory work in `openclaw/` contains real, reusable artifacts: `beleg/bank.clj` (609 LOC, 11 German bank CSV formats + parser + auto-categorizer), `beleg/tax.clj` (660 LOC: UStVA / EÜR / DATEV EXTF exporter / SKR04 mapping), 16 anonymized bank-CSV fixtures, and German tax legislation specs in markdown. Extraction plan: bank.clj → Phase-4 bank-importer module; tax.clj → Phase-2 l10n-de; CSV fixtures → bank-importer test resources; the rest (agent runtime, transcripts, scratch) stays in `openclaw/`. **Flagged: kernel currently lacks analytic accounts (cost-center / profit-center) — beleg has them. Add to roadmap.**

**07 — period semantics comparison.** Concrete walk through Odoo source + SAP/NetSuite/QuickBooks/Xero/Sage docs. Verdict: our current single-lock-state model is the QuickBooks-class minimum and not enough for accountants. **Mandatory before Phase 2-DE**: (a) soft vs hard lock distinction (`:period/locked-at` vs `:period/sealed-at`), (b) special-period flag for DE period 13-16 year-end adjustments, (c) pre-close validation hook (no drafts, no unreconciled, trial-balance-zero). Defer per-user lock exceptions and fiscal-year entity. Drives ADR-014.

**08 — bitemporality evidence.** Sparse production evidence either side. Vendor marketing (XTDB, Datomic) is loud; SMB products (QBO/Xero/NetSuite) carry no bitemporal model and use reverse-and-repost in current open period. Nubank's Cavalcanti talk distinguishes tx-time from business post-date but uses append-only compensating entries, not full valid-time queries. Verdict: **keep but quietly demote** — drop `:posting/valid-to` and `:posting/temporal-key` tuple, keep `:posting/valid-from` (cheap, useful for backdated invoices). Make `:as-of-valid` opt-in; rename `:as-of-tx` to `:as-of-snapshot`. Forward-compatible if a regulated-fintech use case appears later. Drives ADR-008 update.

**09 — HR / personnel / payroll.** Survey of Odoo `hr*`, Tryton `company/employee`, SAP SuccessFactors / S/4HANA HCM, Workday Core HR, Personio. Convergent shape: `:person` (global) + `:employment` (per-entity, effective-dated) — Workday's Worker-with-multi-job pattern. Timesheet IS an analytic-line in Odoo (no new entity needed — reuses ADR-022). Per-jurisdiction payroll routes through a `PayrollProvider` protocol with country-vendor adapters (`kontor-payroll-de-datev`, `kontor-payroll-us-gusto`, `kontor-payroll-br-esocial`, etc.). Two small kernel additions surfaced: bootstrap a `:cost-center` analytic plan; payroll-rule → account via ADR-019 external-codes. Commodity SaaS for ATS / performance / LMS / OKRs / engagement / compensation planning.

**10 — Business-OS companion projects.** Survey of Odoo, Tryton, SAP S/4HANA, Salesforce for the non-HR non-accounting business surface (sales, CRM, procurement, manufacturing, helpdesk, project, marketing, e-commerce, CLM, fleet, asset). Two cross-cutting patterns surface: (a) a `:schedule` entity that depreciation + revrec + subscription + lease + PTO accrual + insurance premium all need — ADR-032 candidate; (b) bootstrap a `:cost-center` analytic plan at kernel install. Build order: ADR-032 → `kontor-partner` → `kontor-sales` → `kontor-procurement` → `kontor-asset` → `kontor-revrec` → `kontor-subscription` → `kontor-project` → `kontor-commerce-adapter` → `kontor-hr` + `kontor-payroll-de-datev`. Defer mfg / helpdesk / field-service / fleet / clm / marketing / crm to commodity SaaS or post-demand. Tryton is the preferred shape-oracle (cleaner state machines than Odoo); Salesforce data model is the oracle for CRM specifically. Identifies the Salesforce admin-tier visual rule editor as the largest remaining gap (simmis opportunity).

**28 — Stage L′ (`kontor-asset`) research-before.** How Odoo handles fixed-asset depreciation ("Abschreibungen") and year-end close + statutory statements ("Jahresabschluss"). `account_asset` is Enterprise-only — the asset half is from Odoo 19 public docs + OCA `account_asset_management` (AGPL-3, reference only): the `account.asset` / `account.asset.line` / `account.asset.profile` shape, the depreciation board (`type = create | depreciate | remove`), methods (`linear`, `degressive`, `degr-linear`), prorata-temporis, acquisition→depreciation→modification→disposal lifecycle. The close half **is** in Community `account` and is cited at file:line — the central finding: **Odoo does not journalize a year-end closing entry**; the P&L→retained-earnings roll is a *reporting convention* (`include_initial_balance` flag + `equity_unaffected` account type + per-expression `date_scope` enum). "Close" = a typed set of lock dates (`fiscalyear_lock_date` soft / `hard_lock_date` irreversible) + a pre-close validation gate (`_validate_locks`: no drafts, no unreconciled lines) + a per-user audited `account.lock_exception` entity. Statements are data: `account.report` / `.line` / `.expression` with a six-value engine enum (`account_codes` prefix-sum, `domain`, `aggregation` cross-line-by-code, `tax_tags`, `external`, `custom`) and root+variant for l10n. Tax-law: Odoo has **no SAP-style depreciation areas** — book-vs-tax = "duplicate the asset, two profiles, two journals" (a documented pain, cautionary); no hardcoded AfA/MACRS tables (left to user, l10n ships *default profiles* as seed; MACRS per-year tables aren't expressible by the method enum). Mapping: needs a **new `:asset` entity** (`:schedule` ADR-032 deliberately doesn't compute amounts); one `:asset` with N ledger/purpose-tagged `:asset-schedule` boards *beats* Odoo on parallel depreciation; year-end close is mostly **reuse** of `kontor.period` + a design call on whether to keep the posted closing entry; cash-flow statement needs **no new generator** once the report engine gains the engine enum + `date_scope` + cross-line aggregation.

**29 — Stage L′ (`kontor-asset`) research-before, Tryton angle.** Companion to note 28 — how **Tryton** (GPLv3, richest *local* reference; patterns only, no code lifted per ADR-001) handles fixed-asset depreciation and year-end close. The asset model `account.asset` / `account.asset.line` / `AssetRevision` is **deliberately minimal**: one method (`linear`), two frequencies, day-prorated first/last periods with a 365-day normalisation, and the whole depreciation table is *materialised* the moment the asset is `run` (`create_lines` → rows; a separate wizard posts them as `account.move`s — `Abschreibung an Kumulierte Abschreibung`, indirect method). Disposal (`get_closing_move`) auto-recognizes gain/loss; revaluation (`AssetUpdate`/`AssetRevision`) is append-only + forward-recompute. The central close finding: Tryton has **two distinct mechanisms** — `BalanceNonDeferral` (a *posted* P&L→equity rollup move = kontor's existing `kontor.closing`) and `FiscalYear.close` (freeze + snapshot every BS account into immutable `account.account.deferral` rows = the half kontor *lacks*). P&L must be zero before `close`; close is gated (no drafts, no un-posted depreciation via the asset module's `check_asset_line_running`, earlier years must close first). Financial statements = the `account.account.type` tree: a `statement` selector (`balance`/`income`/`off-balance`) + role booleans (`assets`/`receivable`/`payable`/`revenue`/`expense`/`stock`/`debt`/`fixed_asset`); the type tree ships **per chart template** (the German chart defines its own ~40-node tree). Tax-law: **no book-vs-tax separation** (one schedule per asset — the headline gap; a DE Handelsbilanz≠Steuerbilanz user is stuck), **no AfA-Tabellen / GWG / degressive**; the entire German asset l10n is *13 lines* flagging two type templates `fixed_asset=True`. Mapping: needs a **new `:asset` + `:asset-line` entity** (not `:schedule-occurrence` — the table is computed up-front); a `DepreciationProvider` protocol turns Tryton's one-method weakness into a kontor strength; book-vs-tax rides the existing `:ledger` substrate (ADR-021) — *kontor structurally beats Tryton here*; year-end close = keep `kontor.closing` as the rollup, **add a deferral-style snapshot** (possibly reusing `:balance-assertion/*`); reconsider a thin `:fiscal-year/*` entity (note 07 deferred it; Tryton's close-ordering invariant makes a fresh case); enrich `:account/type` toward Tryton's `statement` + role-flag lattice and add `:account/fixed-asset?`. Five explicit design calls flagged for AskUserQuestion.

**27 — ADR-049 review-after.** Independent code review of ADR-049 (legal hold) commit `3c3f3cb`. **1 P0** (`purge-targets` only matches the 2-element `[:db/purge eid]` vector — `:db/purgeAttribute`, `:db/retractEntity`, `:db.fn/retractEntity` and entity-map retracts bypass the hold middleware entirely, defeating ADR-049's "no time window in which a purge can fire without consulting holds" thesis for non-posted held entities; matches the Pension Committee / Brookshire fact pattern). **3 P1**: (a) `:pending-review → :released` is in the status-transition seed list but has no approval-policy seed, so a counsel-only workflow `:placed → :pending-review → :released` skips all SoD enforcement; (b) `find-hold-violating-purges` re-evaluates `:scope-query` once per (target × hold) inside the inner loop — O(N×M) datalog calls for batched purges; (c) `:legal-hold/placed-at` is the same denorm the Stage-L review marked for removal on `:credit-hold/placed-at`. **4 P2**: malformed/empty `:scope-query` accepted at placement (loud-fail only at first purge); `active-holds` uses non-idiomatic `(get set ?s)` + `(some?)` datalog; `refresh-scope-eids!` writes invisibly (no audit-doc, no status-history, no side-effect-intent); ADR text mentions a "sweeper" the kernel doesn't ship. **31 — Asset depreciation & year-end close: regulation dimension + `kontor-asset` design.** Stage L′ research-before, the tax-law / regulation agent (siblings study Odoo / Tryton / SAP-NetSuite-Oracle). Maps how depreciation ("Abschreibungen") and Jahresabschluss are *mandated by statute* across DE (HGB §253/§264/§284, EStG §7/§7g, AfA-Tabellen, GWG §6 Abs. 2/2a, the degressive-AfA on/off windows), US (MACRS IRC §168, §168(k) bonus, §179, book/tax divergence), CA (CCA classes + half-year rule), IFRS (IAS 16 cost-vs-revaluation + componentisation, IAS 36 impairment, IFRS 16 ROU), UK (capital allowances). Synthesis: the regulated content is almost all *data* for `kontor-l10n-<cc>`, not mechanism — the ADR-005 split one layer up. **Central design call: a "depreciation area" IS a kontor `:ledger` (ADR-021), not a `:valuation-book` (wrong axis — that's cost-basis selection) and not a new concept** — Handelsbilanz-vs-Steuerbilanz is exactly the parallel-book case ADR-021 was built for (`decisions.md:1012`). Proposes a `DepreciationProvider` protocol (sibling of `TaxProvider`/`CostingProvider`: companion ships straight-line / declining-balance / SYD / units-of-production; l10n ships MACRS / AfA-degressive / CCA / full-expensing), a full `:asset` / `:asset-class` / `:asset-depreciation` / `:asset-event` schema in kontor namespacing with an `:asset/status` lifecycle machine, and composition onto `:schedule` / `kontor.closing` / `:period` / `:status-machine` / `:audit-doc`. Jahresabschluss gap analysis: `kontor.closing` + `compute-statement` cover the GuV/Bilanz/year-end roll; Stage L′ must add the Anlagengitter (HGB §284 Abs. 3 — a generic asset-roll-forward report engine, layout stays l10n) and `compute-cash-flow` + `compute-equity-changes` (two universal statement engines, the only kernel touches). Effective-dated depreciation rules = ADR-026 verbatim, with one deliberate divergence: the selection key is `:asset/acquisition-date`, not `:transaction/effective-date`, because the rule that governs an asset is fixed at acquisition for its whole life. Proposes 4 ADRs for Stage L′ + 7 open design questions.

**32 — Stage M ADR-050 / 051 / 052 review-after.** Independent code review of the back half of Stage M (`kontor-legal`) commits `a722b4f` / `c7e9477` / `8c28c1a` — retention policy + sweeper (ADR-050), `:audit-doc/privilege` (ADR-051), `:dsar-request` + `kontor.dsar/collect` (ADR-052). **1 P0** (ADR-052: `collect` walks only the *direct* partner-attr registry — indirect partner data via `:transaction` → `:payment-application` / `:status-history/origin-transaction`, which note 24 §3.4 specified *twice* as in-scope, is silently missing and *not* listed among ADR-052's deferrals — a consumer DSAR portal ships incomplete access responses believing they're complete). **4 P1**: (a) the `:legal-hold/purge-blocked` exception is double-wrapped by datahike's `[:db.fn/call …]` transactor so consumers can't dispatch on `(:type (ex-data e))` — the type is only on `.getCause`, REPL-confirmed, latent because every test uses `thrown-with-msg?`; (b) `candidate-eids` is an unbounded O(n) full-attribute scan with no `:batch-size` and no `:applies-to` cross-check — a cross-namespace anchor (`:applies-to [:audit-doc]` `:triggered-by :status-history/changed-at`, which the schema doc explicitly advertises) sweeps every `:status-history` row; (c) `supersede-policy!` has no approval-policy seed for `:active → :superseded` — the *exact recurrence* of note 27's P1-1 pattern, and superseding can *shorten* retention (data-destroying); (d) ADR-051's waiver SoD anchors on `:create/uid` = the doc *uploader*, not the *classifier* — "creator ≠ waiver" is the wrong segregation, thinly acknowledged. **3 P2**: `policy-for` non-deterministic on identical `:effective-from`; `retention-deadline` silent-skip on non-Date anchor is correct but gives no operator signal; `dsar/holds-covering` re-implements scope-checking instead of calling `legal-hold` (note 27 said compose, don't re-implement). The retention sweeper itself — the highest-stakes code in the stage — is **sound**: REPL-confirmed that both `:purge` and `:anonymize` route through the ADR-049 hold-middleware and an anonymize-on-held-entity is structurally refused. Cross-checks adopted/diverged against notes 22/23/24 (kernel partner-attr registry complete for all 9 kernel attrs; `:db.purge/attribute` correctly used where note 27 warned `:db/purgeAttribute` doesn't exist) and note 27 (batched `entities-held?` inherited correctly; note 27 P1-1 recurs as this note's P1-3; `:legal-hold/placed-at` denorm appears dropped).
